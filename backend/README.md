# Serenity local backend

Chat and account discovery are documented in [CHAT.md](CHAT.md), including the local demo accounts, owner-supplied sample videos, private-message workflow, and test commands.

Map-based travel discovery is documented in [MAPS.md](MAPS.md): watch a published trip, find its destination, and go experience it. The map and destination picker are separate modules; dates and highlights are retired from active trip information.

On macOS, Serenity can run as a per-user login service using `backend/com.serenity.local.plist`. Once installed in `~/Library/LaunchAgents/`, it starts at login and restarts if it exits. Check it with `launchctl list com.serenity.local`; its logs are in `backend/data/server.stdout.log` and `backend/data/server.stderr.log`. This still only serves `127.0.0.1:8765` on this computer.

Alternatively, double-click `start-serenity.command` in the project folder to start the local server and open the account page. Keep its Terminal window open while using the app. Or start it from the repository root:

```bash
python3 backend/server.py
```

Open **http://127.0.0.1:8765/**. Use **Sign in → Create account** to make a real account, then return to the studio and upload clips. The server uses Python's standard library and SQLite, so it needs no package installation or paid service. Open **Map** from the toolbar to explore public trips with creator-selected destination pins; see [MAPS.md](MAPS.md) for the place-picker workflow, privacy boundaries, service limits, and provider configuration.

On the landing page and app home, the **＋** in the header expands app-level links such as Home feed, published trips in Account, Clip Studio, and Chat. The trip sidebar is available only in Clip Studio and lists trips that contain published clips, with their published clip counts; unpublished or empty feeds do not appear. Use the fixed folder/sidebar control on Clip Studio to open or collapse it. The Home feed search icon beside the Travel details / Video / Creator trips tabs opens an in-place search that filters the currently loaded posts.

The website root (`/`) is the public Discover landing page; its Open app link goes directly to the app. Discover is separate from the five app destinations: Home feed, Map, Chat, Clip Studio, and Account. Chat opens the private messaging inbox (served at `/search.html`); Search is no longer a toolbar destination and remains an independent control on the Home feed. Account includes a gallery of the signed-in user’s published trips, grouped with their videos, plus a side drawer for profile, appearance, and playback settings. The app toolbar contains those five destinations and is swipeable on touch devices. Clip Studio is the single workspace for creating named trips, editing their descriptions, and uploading or removing their videos. Motion is reduced when the device requests reduced motion.

The app can be installed from its Home feed page in browsers that support web app installation. The installed app opens directly to the Home feed rather than the Discover website. A service worker caches the app's static shell for offline launch; account data, private media, and API responses are never cached by it, so signing in and loading trips or feeds still require the server. On iPhone or iPad, use the browser's Share menu and choose **Add to Home Screen** if the Install app button is not available. Installability on a public server requires HTTPS; localhost is treated as secure for local testing.

Selecting **Account** shows a profile, your published-trip gallery, and saved public videos; sign in to load and manage those galleries. Remove saved videos from the Account page. The settings drawer contains identity, colour-scheme, and device-local autoplay settings. Manage trips and unpublished videos together in **Clip Studio**. Each account has a unique username and stable public ID. Share the public profile link to show that user’s publicly published trips. Email, theme, trip notes, and unpublished videos remain private. Instagram and TikTok accounts are not connected or imported; the profile currently uses Serenity account data.

Account records, unique usernames and public IDs, session hashes, themes, named trips/feeds, up to 500 video clips per feed, trip details, and private trip notes are stored in `backend/data/`. Public profiles use fresh, uncached responses and never fall back to saved listings: making a video private must remove it from subsequent profile requests. Videos are stored as files in the private uploads directory, while the database records ownership and publication. Users can create as many named trips as they need in Clip Studio. Every trip has its own `feed.html?feed=ID` page; owners can view their saved private clips there, while visitors see only published posts. Each clip is limited to 50 MB. This directory is gitignored. Back it up to preserve accounts and media. Passwords are stored as salted PBKDF2-SHA256 hashes; login uses an HTTP-only, same-site session cookie. The server only binds to your computer's loopback address.

In **Clip Studio**, choose videos, choose a folder, or drop a folder containing up to 500 videos (50 MB each). **Find my trips** samples three frames per video, sequentially, and uses on-device CLIP zero-shot image classification to suggest visual-theme groups. Nested folders remain separate; no cities, GPS coordinates, or travel dates are inferred. Ambiguous scenes go into **Needs a closer look**. Review thumbnails, rename groups, merge groups, create a group, or move/exclude individual videos before saving. Exact duplicates within the selected collection are excluded using SHA-256. They are not compared with previous collections. Browser-supported MP4, MOV, WebM, and M4V files are accepted; codec support still depends on the browser. Undecodable files are listed rather than assigned invented themes.

The first analysis downloads Transformers.js 3.8.1 from jsDelivr and quantized `Xenova/clip-vit-base-patch32` model files from Hugging Face. This needs an internet connection and may take several minutes; the browser can cache model downloads. Inference runs in a Web Worker using WASM, with no paid API or API key. Only model assets are fetched externally: video frames, file names, and folder paths are not sent to an AI service. Download bandwidth, device memory, and CPU are still required. If the model cannot run, **Group without vision** provides explicitly manual grouping. This is scene categorization, not reliable identification of distinct real-world journeys.

After categorization, choose **Post trips to Home feed** or **Save privately**. Nothing is posted until the user chooses. Posting uploads the selected clips, then publishes each group atomically. Missing destinations are labelled **Location not specified** and blank stories use the saved trip name; no inferred city is invented and these optional fields no longer block publishing. A signed-in account is required. Signing in can open in another tab so selected files stay available. Files and review edits remain in memory until saved; keep the tab open. Uploads run one at a time. Stop/retry preserves completed uploads during the same session; account-scoped import and upload keys prevent duplicate trips or videos after ambiguous responses or simultaneous retries. Refreshing does not restore an unfinished collection. Re-selecting files begins a new import. `POST /api/studio/import` creates reviewed private trips, authenticated clip uploads attach videos to their feed IDs, and `PUT /api/feeds/ID/visibility` publishes only the imported clip IDs. Failed publication leaves saved clips intact and retry is idempotent.

Every saved Clip Studio tile has a **Public**, **Private**, **Mixed**, or **No videos** badge directly on its preview, with public/private counts below it. **Post trip to Home feed** and **Make trip private** work without expanding the tile. For multi-video trips, the current preview video also has an individual visibility control. Mixed means some clips are public and others remain private. New uploads do not inherit a persistent public setting; the badge always reflects actual saved clip visibility. Making content private sets `posts.is_public=0`, retaining its saved file, post ID, likes, saves, and comments for later republication. All public feed, profile, related-trip, video, comment, like, and save routes filter out private posts, including direct post URLs. Already downloaded copies cannot be revoked. The separate **Delete moment** action still permanently removes the post and its interactions.

Publishing controls live in `studio-publication.js` and `studio-publication.css`; backend visibility changes live in `backend/trip_visibility.py`. The endpoint supports a whole trip or 1–500 explicitly selected clip IDs, validates ownership before changing anything, and changes each trip in one database transaction. Run `node backend/test_studio_publication.js` for badge-state tests. Backend integration tests cover missing optional metadata, public/mixed/private transitions, idempotent retries, 500-clip selection, unauthorized requests, direct URL privacy, public profiles, and preserving interactions across republication.

Chrome was exercised with a temporary account/database in an isolated private window: post one preview video (Mixed), post the remaining trip (Public), confirm Home feed appearance, make the trip private without expanding its tile, and confirm Home feed removal. A separate collection was then visually categorized, posted directly from the review with an empty destination, and verified on Home feed with its Public preview badge.

The optional **Prefer to build a trip yourself?** form retains the existing create-and-publish flow. That form and later videos added directly to a trip card publish to Home feed using its destination pin and experience/story. Existing private saved videos can also be published together from their trip card. The Account gallery contains only the signed-in user's published videos, grouped by trip; the old `/my-clips.html` URL redirects to that gallery. Private videos can be played in their Clip Studio trip's management section and on the corresponding trip page by their owner. Trip pages show public videos to visitors, while authenticated owners also see their private saved clips, details, and notes. On mobile, use the tabs or swipe between trip videos and private notes.

Home feed displays public travel posts published by accounts on this local server. Only published clips appear: private collection imports do not create public posts unless the user opts in. Clips from the same trip appear together in one swipeable feed card in the order they were added. The viewer fills the area between the header and bottom edge while preserving each video's original proportions, letterboxing where necessary; the navigation toolbar floats over the video. The active clip autoplays muted while its card is in view; on-video controls handle playback, sound, and seeking, while likes, saves, comments, and deletion apply to the currently selected clip. Each public post carries the trip destination and experience/story, and is visible to other accounts on the server and on the matching trip page. Signed-in users can like, save, and comment; saved videos are available from Account. Creators can remove their own posts without deleting the underlying saved clip.

Home feed now opens a video viewer independently of Clip Studio. A persistent tab bar sits above each video's media and highlights the selected Travel details, Video, or Creator trips panel. The details panel is available to the left of the video and the creator's earlier published trips to the right; horizontal swipes and tabs navigate between them. Scroll vertically for published videos. Left/Right arrow keys navigate panels, Escape returns to the video, and Up/Down arrows navigate posts when the viewer has focus. Only the visible center video plays, starting muted; side panels, comments, hidden tabs, and Clip Studio pause it. New pages load near the end of the timeline, with Load more as a fallback. Reduced-motion users start with paused videos.

The viewer lives in `feed-hub.js` and `feed-hub.css`; post interactions remain in `social-feed.js`. Home videos use `object-fit: contain` to preserve their native proportions, with dark letterboxing where needed. The toolbar changes to an accessible icon-only layout from the second active post onward; captions, actions, comments, and playback progress reserve space above it. `GET /api/posts/POST_ID/context` supplies published destination, caption, tip, and the creator's other published trips, excluding the current trip and posts newer than the current video. An exact destination match is ranked first, followed by publication date. It reads no private notes or device GPS. It includes the creator-selected saved destination pin only for a public post. Travel panels clearly label creator-supplied locations as unverified. The travel panel now focuses on a working map link and directions to the creator-selected destination rather than inactive flight/itinerary placeholders. No paid API is invoked by the viewer. Their response fields (`approximate_location`, `flights_status`, `itinerary_status`) reserve a boundary for those future services without presenting invented results. The separate Clip Studio analysis does not populate those fields.

Run `python3 backend/test_server.py` for account/privacy/API integration tests. `node backend/test_feed_hub.js` runs dependency-free event tests for swipe direction, keyboard access, context loading, focus, and playback lifecycle when Node is installed.

Collection code is isolated in `studio-import.js` (UI/save workflow), `studio-video-analysis.js` (bounded decoding/fingerprints/worker client), `studio-vision-worker.js` (model inference), `studio-grouping.js` (pure grouping rules), `studio-import.css`, and `backend/studio_import.py` (private import persistence). Run `node backend/test_studio_grouping.js` for dependency-free grouping checks. Backend tests cover private imports, ownership, batches larger than the previous six-clip limit, manifest conflicts, Unicode filenames, and sequential/concurrent retry safety. Safari was exercised end-to-end against an isolated temporary database: choose a folder containing two identical MP4s, infer Gardens & wildlife from three flower frames, exclude the duplicate, rename the group, save one private trip, open its feed, and play its saved video. Large-device performance and other browser/codec combinations still need broader testing.

New account passwords must be 8–16 characters. Existing accounts with longer passwords can still sign in.

This is a **local development backend**. Its profile links work on this machine, but it is not reachable by friends on other devices and accounts are not shared across computers. Do not expose port 8765 directly to the internet. Public hosting needs HTTPS, an appropriate storage and backup plan, and deployment-specific security work before profile links can be shared externally. Google, Apple, Microsoft, GitHub, and ChatGPT sign-in remain unavailable until provider credentials or partner access are configured.

## Portable Docker deployment

For a shared multi-device install, deploy this Python backend on a host with Docker, a stable HTTPS domain, and durable storage. `Dockerfile` runs the existing account-based API; `compose.yaml` keeps the SQLite database and uploaded videos together in the named `serenity_data` volume. The volume survives image rebuilds and container replacements on that host. Keep the same volume name and host when updating. Do not run `docker compose down -v` or remove the volume: that deletes account and video data.

Configure the host's HTTPS reverse proxy to forward the domain to `127.0.0.1:8765`, then start Serenity from the project directory with that domain:

```bash
ROAM_PUBLIC_ORIGIN=https://serenity.example.com docker compose up --build -d
```

Replace the example domain with the actual public HTTPS origin. Compose deliberately publishes the backend only on host loopback; do not expose port 8765 directly to the internet. The backend sets secure session cookies for the configured HTTPS origin. Sign in to this one deployment from each device; account ownership, trip details, published status, and video files are read from the same server-side database and volume. Source updates preserve data when the named volume is retained.

This deployment starts with a new volume. Existing local data in `backend/data/` is not included in the Docker image or automatically transferred; it remains on the current computer. Docker is not installed in the current development environment, so the container build and public HTTPS deployment have not been run here. For managed container hosts, attach durable storage at `/data` and configure the same environment variables; an ephemeral container filesystem is not sufficient.
